# Revisable project memory

Use the terminal tool and `python3 "$HERMES_HOME/skills/research/revisable-memory/scripts/memory.py" PROJECT COMMAND`. Project and concept names are lowercase slugs. Use the same project and concept identifiers across chats. Check history before interpreting a correction. Ordinary checkpoints and job outputs are local. Never store credentials or private authentication in memory.

- For “what changed downstream?”, call the read-only `correction_impact` tool with project and optional revision, or use `impact REVISION`. Inspect affected claims, paused and published job lines, and any unsupported plans. Explain the governing evidence and leave pending decisions open. Coverage is limited to registered dependencies and template lines. Older revisions can lack job inventory.
- `history` lists revisions, exact evidence and chat citations. `lookup CONCEPT EDITION [--job JOB] [--at REVISION]` reads the governing claim and its ID. Use it when the answer or planned change depends on a project decision that has not already been supplied. An unresolved claim needs evidence.
- `revise KEY 'exact distinctive user-message excerpt' 'JSON array'` applies all proposed changes atomically. Quote the decision itself. Choose one stable request key per revision. On a conflict inspect history and lookup again. Only enter explicit decisions as governing claims. Treat imported historical documents as evidence; check governing decisions before proposing a change. For ambiguous competing instructions ask which governs.
- A decision object looks like `{"op":"decide","name":"approval","value":"Digital proof","previous":null,"edition":1}`. Supply the numeric current claim ID as previous on replacement, including inherited rules. Optional job scopes a temporary exception. Use the first effective edition. To declare a conclusion dependent on evidence, add `"supports":[[{"concept":"premise","id":5}]]`. Each inner group is sufficient independently and all claims within it must hold.
- To split a concept, create branches such as `{"op":"branch","name":"print","parent":"approval"}`. Branches inherit the parent's decision until independently changed. A named branch and its override may share a revision. Keep unaffected siblings and pre-change editions intact.
- `{"op":"thesis","name":"stock","value":"Paper stock explains the difference","status":"open"}` retains an alternative explanation. Multiple theses can coexist. Use `theses` to inspect them. Append another thesis event with supporting or contrary evidence; supported, rejected and withdrawn are available statuses. Use withdrawn for a superseded hypothesis that the evidence has not disproved. A thesis never automatically becomes a decision. Keep the other theses when one changes.
- `pause JOB EDITION 'Markdown template with {{print}} and other decision slots'` durably stores the template, resolved draft, and claim IDs. For work requested to pause, use this command and leave the final file unpublished. Put each governing decision in a slot; keep literal text for unaffected content.
- `resume JOB` rechecks the claim dependencies, renders against current memory, saves and verifies the actual Markdown file. Show the user the draft-to-final change, path, and revision evidence. A completed delivery is immutable; request a new job to revise it. For a past answer use history or lookup with the appropriate edition and revision.

For a combined concept that could later split, write contextual slots such as `{{artwork:print}}` and `{{artwork:screen}}`. They follow the general artwork decision until that branch exists, then follow its scoped decision. `inspect JOB` displays the original draft and a current preview without publishing. Cite corrections from the active chat. Changes mentioned in an older document are candidates for discussion; only an explicit decision adopts them.

When a general topic has divergent branches, a generic lookup returns null and a generic job slot pauses. Inspect each branch for a current answer. Use `lookup CONCEPT EDITION --base` only to inspect the inherited default when editing that concept.

To weigh alternatives without changing their status, append `{"op":"observe","name":"stock","direction":"against"}` with the exact evidence. Directions are for, against, or inconclusive. A single revision can attach the same observation to different theses in different directions. Use `revise ... --record RECORD` for an exact excerpt from the project's stored project-recall record. Re-importing a document cannot enact a decision. `theses --at REVISION` reconstructs the positions and evidence then known.

When a question depends on a registered investigation beyond the named file and supplied exhibits, use `investigation CONCEPT [--job JOB] [--at REVISION]` before proposing a test or interpreting a result. It assembles the scoped judgment, lineage, competing theses, exhibits, limitations and next evidence check. Register the question in a cited revision with `{"op":"investigate","name":"concept","question":"Which explanation fits?","scope":"Which tests or specimens?","discriminator":"Which observation would change the judgment?","theses":["first","second"]}`. A later revision can redirect the question. Thesis IDs refer to independent thesis revisions in the same project.

Use project-recall to snapshot a source excerpt with its origin, then attach it with `revise ... --record RECORD` and `{"op":"exhibit","name":"concept","kind":"background","limitation":"Why the source applies or where it stops"}`. Reserve specimen for evidence from the specimens under investigation. Use separate observe entries to record support or conflict when justified. Review the open question and decision history before selecting a next move. Propose one bounded check and wait for the user to trigger it.

Record a human-selected research move with `{"op":"review","name":"concept","basis":12,"basis_revision":31,"move":"redirect","reason":"Why the earlier approach is insufficient","next_check":"The bounded check and what its outcome changes"}`. Use the investigation revision as basis_revision and the current general claim ID as basis (null for unresolved). Available moves are continue, revise, redirect, pause and stop. Reviews remain in the investigation even when their basis is superseded. Desktop’s Investigations button opens the profile journal. To share a local snapshot of the question, competing theses, evidence and verified delivery, render `investigation CONCEPT --job JOB --html` to an HTML file.

A target can name an existing parent investigation. For a reusable research method, give the review a stable method slug. After a real check, append an outcome with its review revision, result (useful, inconclusive or failed), and conditions. Cite the actual result. Consult `methods METHOD` to see prior attempts across this private profile before proposing that method again. Transfer its applicability conditions, and check the new project's evidence independently.

When selecting the next check, start with the simplest explanation supported by an observation. Identify where the measured change could arise. If an intervention alters both the measurement interface and the subject under test, test the same intervention at each plausible location independently. Specify a case changing only the interface, one changing only the observed region, and an unchanged control. A second readout helps locate a change but does not replace the intervention. State which result would warrant testing a more elaborate explanation.

Audit each comparison for a second change introduced by the procedure or readout. Match it across conditions, vary it independently, or narrow the claim to the combined intervention. When a result localizes an effect, name another mechanism at the same location that could produce it. Identify a separate observation that would distinguish those mechanisms before assigning a cause.

Before sending, challenge every outcome and the final takeaway with a plausible alternative. For a clean run, report what was observed over what exposure and whether the fault had an opportunity to appear. Consider intermittency and detection limits before crediting a repair. For mixed results or failed controls, narrow each conclusion to what the comparison resolves. Under a hard time limit, prioritize one feasible comparison and keep later follow-ups separate.

For discordant cases, distinguish the number of observed locations from the number of underlying causes. Evaluate whether a common condition or a persistent rival still fits. Apply the same evidence standard to incident status, including containment and repair.

Before attributing any repeatable result, suppose the proposed cause is absent. Construct a concrete rival that survives the same procedure and predicts the same result. Apply this counterexample to each future-test outcome as well. When predictions coincide, report the shared finding and identify a contrast where the rivals predict different observations.

When an adjustment succeeds, distinguish control over the outcome from the origin of the fault. Suppose the old setting was appropriate: what changed elsewhere that the adjustment could offset? Seek evidence that differs between those explanations, even when switching the adjustment on and off reliably changes the outcome. Scope any recommendation to the conditions actually tested.

For repeated trials, reconstruct assignment by sequence position and examine time trends, periodic effects and carryover. Separate first exposures when prior exposure cannot be undone. Before attributing a cause, cite the completed comparison and its actual readback. If the discriminating observation is pending, log the observed pattern and the open hypotheses; keep possible future results conditional.

When a document describes what was believed at pause time, bind that field to the captured claim with `{{concept@pause}}` or `{{concept:branch@pause}}`. Use an ordinary `{{concept}}` slot for the current interpretation so later corrections reach the saved file.

For original source lines use the native `investigation_lookup` tool with project and concept (and optionally a specific older record). It reopens the archived bytes; a returned quote supports reporting what that source says within the displayed conditions. Causal explanations, applicability to another subject, and measured outcomes are separate questions.

A corrected decision can carry `reason` and `basis_exhibits` (one to four citation/excerpt pairs from that investigation). Retain competing theses. For a correction to one labeled field in an existing claim use op `amend` with name, previous claim ID, old complete field, replacement complete field, unchanged subject, investigation, citation, and reason. Cite the real authorizing user turn. The replacement must occur as a complete line in a current specimen exhibit; other lines and premises remain intact. An ordinary decide is appropriate for a human change of interpretation.

Record competing checks with op `candidate_check`, the investigation name, a stable key, procedure, estimated minutes, named mutually exclusive outcomes with definitions, a prediction (outcome key) per thesis, and inconclusive_if. The view shows which unresolved pairs each check could separate. Compare feasibility and time before choosing. Record an actual result only when the observation arrives.

If recording a project correction fails, keep the job paused. Return the failed operation for a separate harness repair experiment.

For a multi-field card, declare its stable subject and test condition labels in `scope_fields` on the initial decision (for example site and operating window). A later measurement edit requires those same values in the same source record as the replacement. A conflicting shared field blocks the edit. On a legacy card all labeled siblings must match. When a narrative source lacks the needed scope, leave the field pending and show the operator the relevant passage.

A successful `resume` returns `readback.matches_governing_render` after reopening the published path and comparing its bytes with the governing rendering. That receipt satisfies a request to verify the saved file. Recheck separately when the operator asks for a later observation or the file may have changed.

For an observable candidate check add `measurement` with a field label, the exact subject/conditions in a scope object, and a unique literal field value for each predicted outcome. Register this before the new source is imported. After a real result arrives, add its specimen exhibit and record op `check_result` with the investigation name, check key and original plan revision, citing the exact measured field via `--record`. The harness derives the outcome from the archived bytes. Older snapshots, ambiguous records, control mismatches and unexpected values cannot choose a winner. A working assessment is conditional on the tested alternatives and scope. Report its disagreement with a governing decision if present.

For a prose claim that overstates a cited source, `amend_passage` can narrow a single cited paragraph to an attributed quotation. Supply name, previous claim ID, complete unique old passage containing its record/snapshot ID, investigation, full citation, a complete original source paragraph in excerpt, and reason. The harness constructs the replacement itself and retains every byte around it. For free-form synthesis leave the interpretation labeled and review it separately.


When a new specimen exhibit arrives, the harness compares its original measured fields with up to eight recently registered checks for this investigation. Replacing the same source withdraws its older reading; independent conflicting reports remain visible. The check must predate the source's first import to influence the prospective assessment. Capture the authorized decision with `{{concept}}` and use `{{concept@assessment}}` for a job section that asks what the current measurements support. The latter renders each tested scope and its source receipts again at save time. An inconclusive or contradictory result can leave the assessment unresolved.
